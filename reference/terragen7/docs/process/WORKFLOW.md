# 协作流程（WORKFLOW）

## 1. 角色

| 角色 | 担任者 | 职责 |
|---|---|---|
| 决策者 | 用户 | 确认计划与 §00.8 待定问题；在每个里程碑闸门查看成果并批准继续；可随时调整参数或优先级 |
| 架构师 / 审核者 | Claude Opus 5.5（本会话或 `claude --model opus` 新会话）| 维护规格（`docs/plan/`）与任务卡；派发任务；审核代码、数值与图像；合并；写里程碑总结 |
| 执行者 | Claude Sonnet 5（默认）/ Claude Haiku 4.5（机械性任务）| 按任务卡实现代码、测试、审查图与报告；不修改规格 |

## 2. 工件

| 路径 | 内容 | 谁写 |
|---|---|---|
| `docs/plan/*.md` | 规格（契约），章节号稳定 | 审核者 |
| `docs/plan/CHANGELOG.md` | 规格变更记录（日期、章节、原因、影响任务）| 审核者 |
| `docs/tasks/INDEX.md` | 任务总表、依赖、推荐模型 | 审核者 |
| `docs/tasks/M*-*.md` | 任务卡 | 审核者 |
| `docs/tasks/STATUS.md` | 每个任务的状态与当前轮次 | 仅审核者 |
| `docs/reports/Txx.md` | 执行报告（每轮追加一节）| 执行者 |
| `docs/reviews/Txx-rN.md` | 第 N 轮审核意见 | 审核者 |
| `docs/reviews/Mx-summary.md` | 里程碑总结（含图、指标、耗时）| 审核者 |
| `artifacts/Txx/` | 审查图、指标 JSON、基准输出（不入 git）| 执行者 |

## 3. Git 约定

- `main` 只由审核者合并（`git merge --no-ff task/Txx-slug`）。
- 每个任务一个分支 `task/Txx-<slug>`，从最新 `main` 创建；并行任务使用独立 worktree。
- 提交信息：`Txx: <简述>`；修订轮：`Txx r2: <简述>`。
- 合并前审核者在分支上 rebase 到最新 main 并重跑 `scripts/check.sh`。

## 4. 任务生命周期

```
READY ──派发──▶ IN_PROGRESS ──提交──▶ SUBMITTED ──▶ IN_REVIEW
                    ▲                                   │
                    └──────── CHANGES_REQUESTED ◀───────┤
                                                        ├──▶ ACCEPTED ──▶ MERGED
                    BLOCKED（规格问题）◀────────────────┘
```

- **BLOCKED**：执行者遇到规格矛盾或重大未定设计时，停止并在报告中写明问题、选项与建议。审核者修改规格（记入 CHANGELOG）或答复后转回 IN_PROGRESS。
- **轮次上限 3**：第 3 轮仍未通过时，审核者选择：拆分任务 / 重写任务卡 / 亲自实现困难部分（在报告中注明），不无限循环。
- 依赖任务未 MERGED 前，后继任务不得派发（除非任务卡注明可基于接口桩并行）。

## 5. 两种运行模式

### 模式 A：审核者编排（推荐）

用户在审核者会话中说“执行 M1”（或“执行 T10”）。审核者：

1. 检查依赖均已合并，按 INDEX 选出可并行的任务。
2. 用 Agent 工具派发：`model: "sonnet"`（或 `"haiku"`）、`isolation: "worktree"`，提示词为 §7.1 模板。互不依赖的任务在同一条消息中并行派发。
3. 执行者完成后，审核者按 `REVIEW.md` 审核，在 `docs/reviews/` 写意见。
4. 需修改时用 SendMessage 把审核文件路径发回**同一个执行者**（保留其上下文），提示词为 §7.2 模板。
5. 通过后合并、更新 STATUS。一个里程碑全部完成后写里程碑总结并**停下来等待用户批准**。

### 模式 B：用户手动

1. 用户在仓库目录开新会话：`claude --model sonnet`（或 haiku），粘贴 §7.1 模板（替换任务号）。
2. 执行者完成后，用户回到审核者会话说“审核 Txx”。
3. 若需修改，用户把 §7.2 模板发给执行者会话；循环直到 ACCEPTED。

## 7. 提示词模板

### 7.1 执行者初始提示词

```
你是 TerraGen7 项目的执行者，负责任务 {Txx}。
1. 先完整阅读 docs/process/EXECUTOR.md 并严格遵守（尤其是隔离规则）。
2. 阅读任务卡：docs/tasks/INDEX.md 中 {Txx} 所在的里程碑文件里 “### {Txx}” 一节，以及卡片“必读”列出的规格章节。
3. 按 EXECUTOR.md 的步骤完成：分支 → 实现 → 测试 → scripts/check.sh → 审查图 → 报告 docs/reports/{Txx}.md → 提交。
4. 不要合并到 main，不要修改 docs/plan/。遇到规格矛盾或重大未定设计，按 BLOCKED 流程报告后停止。
完成后用一段话总结：做了什么、测试结果、偏差与未解决问题、报告路径。
```

### 7.2 执行者修订提示词

```
任务 {Txx} 的第 {N} 轮审核意见在 docs/reviews/{Txx}-r{N}.md。
逐条处理所有 BLOCKER 与 MAJOR（MINOR 尽量处理，NIT 可选）。
在 docs/reports/{Txx}.md 末尾追加 “## 第 {N+1} 轮” 一节，逐条对应说明处理方式（已修复/不同意及理由）。
重新运行 scripts/check.sh 与卡片要求的测试和审查图，然后提交 “{Txx} r{N+1}: ...”。
```

## 8. 规格变更

- 只有审核者修改 `docs/plan/`；每次修改在 `CHANGELOG.md` 记录并在受影响任务卡中注明。
- 执行者的接口变更申请（ICR）写在报告的 “ICR” 节：动机、提议的签名、影响范围。审核者批准后更新规格。

## 9. 并行规则

- 同时进行的任务不得修改同一文件，工作区 `Cargo.toml` 的 members 列表与“注册表”类文件（如 refine 字段注册表 `registry.rs`）除外，冲突由审核者合并时解决。
- **磁盘约束**：并发 worktree ≤ 2，全部共享 `CARGO_TARGET_DIR`（§08.1）；合并后立即删除 worktree。
- T00 一次性创建所有 crate 的空骨架，以减少后续冲突。
