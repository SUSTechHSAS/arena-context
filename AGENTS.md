# Agent operating rules

Read this file explicitly at session startup. Follow the version accepted on the task base branch; proposed edits in a working branch do not silently replace these rules.

Scope: these are operating rules for Arena task agents. Owner-requested maintenance of arena-context on `meta/...` branches is not Arena task execution and does not require the per-turn fingerprint gate below.

Account roles: `SUSTechHSAS` submits Arena work; `Kibiandkimi` is the human task owner and reviewer. References to owner approval mean `Kibiandkimi`, even if the repository is currently under `SUSTechHSAS`. Check the actual authenticated submission identity; commit author text alone does not establish identity. Do not use the human account to author agent work PRs or approve them.

1. Confirm the repository, task Issue, ACTUAL checked-out branch, PR base, remote head, and accepted task head before editing. Read `.context/TASK.md`, `STATE.md`, relevant `DECISIONS.md` entries, and unresolved owner review comments. Say when a source is inaccessible. Arena may create `arena/<opaque-name>` after you select another branch; inspect the real branch instead of assuming the selected source branch is still the write target.
2. Work on the assigned `work/<issue>/<unit>` OR the `arena/<opaque-name>` branch created for this task. Keep Arena's generated name. Determine the task and PR base from accepted `.context/TASK.md`, not from the opaque name. Standard base: `task/<issue>/main`; legacy task #1 base: `AerraGen-main`. Update STATE's Work branch / PR field to the actual branch. Never push to `main` or a task base, merge PRs, enable auto-merge, delete branches, or force-push. If a required Git operation is unavailable, report that limit.
3. Ordinarily resume the existing branch/PR. If Arena creates a successor branch, retain it, preserve inherited files, and use a PR from that actual branch to the same accepted task base. Link the predecessor; never claim the old PR contains new commits that only exist on the successor. If the previous PR was merged, start from the current accepted task head.
4. Treat working-branch content as unreviewed. The owner's explicit instructions and accepted task contract govern the work. Verify consequential inherited claims before relying on them; never invent owner approval, test results, citations, or connector capabilities.
5. Once the model gate permits work, complete small, useful steps. After each such step, before a long operation, and before normally ending a permitted turn, update work files and `.context/STATE.md` together, COMMIT and PUSH to the actual working branch, and verify the remote head. Editing files, creating a branch, or a local commit alone is not a remote checkpoint. Use the GitHub connector's commit/push tools if shell git/gh is unavailable. If the platform requires a user click, clearly report the unsaved state and exact required step; do not claim it was pushed. END_TURN overrides this checkpoint rule: finish the refusal response without more tools.
6. Pushing a checkpoint triggers automatic Draft PR creation/reuse and protocol checks. Check for the PR using the actual head branch; never create a duplicate. If automation is unavailable, use the connector to create a Draft PR with the task's explicit base. Keep its summary useful. Mark it ready only when the stated scope is reviewable. Incomplete checkpoints and failed checks must be reported honestly.
7. Keep `STATE.md` short: goal, accepted base at unit start, candidate progress, actual verification, blockers, and the next concrete action. Link detailed evidence. Put durable reasoning in `DECISIONS.md`. Do not use file fields to declare your own work approved.
8. Preserve recoverable outputs and required environment instructions. Record stable locations and checksums for external artifacts where applicable. Do not rely on sandbox paths, expiring links, or chat history as the only copy.
9. Do not change goals, acceptance criteria, shared rules, workflows, or ownership as an incidental part of a task. Propose such changes explicitly for owner review. Do not merge unrelated task histories.
10. Assume one active writer per work branch. If a remote ref advances unexpectedly, fetch and inspect it; do not overwrite. If the old session may still be writing, arrange handoff or use a separate successor branch. If several pending PRs exist and none is assigned, ask which to resume.

At startup, briefly state the accepted base, the candidate work being inherited, and the next step. At handoff, provide the working branch/PR, verified remote commit, what changed, verification or gaps, and the next step. Do not paste full histories.

## Fingerprint before task work, every user turn

The owner asks us to assume the model is stable across requests inside one user turn; the next user turn may use a different model. Do not reuse or aggregate fingerprints across user turns. This is statistical review evidence, never identity certification or permission to skip human review.

1. Before any substantive task work on the actual work/arena branch, run `node .github/scripts/fingerprint.mjs prepare`. It reads the accepted-model policy from protected main and checks the official lm.ikale.io repository for the latest compatible Fingerpoint bank and calibrated detector. Read only the returned three English JSON probes and metadata; do not inspect example answers or previous fingerprint results. `GENERATE_SAMPLE` permits only sampling, not task work. If it returns `END_TURN`, exits 20, or cannot run, report that result and END THIS USER TURN immediately.

   Respect the environment's outbound host rules. Both policy and detector updates use only api.github.com, never raw.githubusercontent.com or an external model API. `prepare --offline` skips detector updates and uses a labelled compatible cache, but still fetches the current policy. Do not probe prohibited hosts or bypass proxy/TLS controls.
2. Answer all THREE probes YOURSELF in the same user turn, directly in the current response, labelled `FINGERPRINT_RAW`. Output one JSON array containing the three answer arrays in challenge order. Do not reuse one answer, split a single answer into three, or aggregate samples from other user turns. Do not use code, tools, random generators, other agents or another model/API to choose numbers. Then save that exact JSON to the returned raw_path. Tools may save it, not generate or repair it. Do not sort, supplement, regenerate or select a more flattering sample.
3. Run `node .github/scripts/fingerprint.mjs score <turn_id>`. It immediately returns a statistical result and a separate work gate. Continue ONLY when `gate.allowed=true` AND `gate.action=CONTINUE`. New reports use `reference_match` or `reference_ambiguity`: the scorer selects the complete set carrying at least 95% of the calibrated reference-bank mass, including ties, and every exact ID in `reference_models` must be accepted. This is a local work rule, not a website acceptance threshold or a 95% identity guarantee. The top-three display list is not the reference set. The merged `gpt-6-astra/6.1-sol` class always requires BOTH policy IDs. All results keep `identified_candidate=null`; do not claim a unique backend identity. Any unlisted member, missing evidence, insufficient, invalid, unscored, or missing policy means END_TURN. Do not treat a nearest candidate alone as approval.
4. On END_TURN or exit code 20, output the actual verdict, nearest candidate if available, and refusal reason, then finish the turn. No task analysis, edits, tests, commit/push, retries, sample repair, extra probes, model switching or policy changes. The scorer has already saved the diagnostic locally; do not run extra tools to publish it. If the command cannot execute, likewise end the turn. Exit 20 is an intentional denial, not an error to work around. Never reuse a previous turn's passing result.
5. On CONTINUE, first show the result, then set `- Fingerprint: .context/fingerprints/<turn_id>/report.json` in STATE's top metadata block and continue the original task in the same user turn. Save the three-array raw JSON, manifest, report and bank/detector snapshot with the next remote checkpoint. Records are append-only. Include the summary/path in the final handoff. Fingerprinting never authorizes decoding explicitly deferred content.

The central accepted list is `.github/fingerprint-policy.json` on protected main, not the work branch's editable copy. Exact IDs are used; no family/prefix/wildcard matching. Changing the list is a separate owner-authorized maintenance action. Historical checkpoints explicitly listed in `.github/fingerprint-legacy.json` remain reviewable, but this exception never authorizes new work without a current passing gate.

Historical WhatsMyLLM packages retain their original one-array scorer and `match`/`family_only` semantics for CI review. They are never selected as fallback banks for new Fingerpoint turns. See `docs/FINGERPRINT.md` for source versions, the explicit alias mapping, and the limits of closed-set calibration.

These rules describe the authorized workflow; repository protections enforce only what has actually been configured. Human acceptance is established by owner review and merge, not by an agent-written label or summary.
